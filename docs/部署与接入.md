## 二、门户侧要做的事

### 1. 注册本应用（否则 SSO 回跳会被 403）

在门户「应用管理」里新增一条记录：

| 字段 | 值 |
|---|---|
| 名称 | 自动询价系统 |
| URL | `http://<本应用IP>:6900/` |
| 图标 | 任意 Emoji，如 `🔍` |
| 分类 | 采购 |
| 打开方式 | `new_tab`（或 `embedded`） |
| 可见角色 | 按需绑定（不绑 = 所有登录用户可见） |

> **必须与 SSO 回调同源**：门户在签发登录凭据前，会用 redirect 目标反查应用表，
> 要求 `scheme + host + port` 完全一致。本应用的回调是
> `http://<本应用IP>:6900/api/auth/sso/callback`，所以注册地址的 origin 必须是 `http://<本应用IP>:6900`。

### 2. 共享密钥

把门户 `.env` 里的 `JWT_SECRET` **原样**复制到本应用的 `.env`。
两边不一致时表现为：登录能跳回来，但接口持续 401。

### 关于「退出登录」

点击退出后的实际动作（三步）：

1. `POST /api/auth/logout` —— 清掉**本应用**的会话 cookie；
2. 用一个**隐藏 iframe** 去请求门户登出地址（`PORTAL_LOGOUT_URL`）—— 目的是让**门户**把自己的会话也清掉；
3. 让**顶层窗口**跳到门户登录页（`SSO_LOGIN_URL`）。

```env
# ② 隐藏 iframe 请求的门户登出地址；③ 的登录页地址复用 SSO_LOGIN_URL
PORTAL_LOGOUT_URL=http://192.168.40.194:6690/logout
```

**为什么用隐藏 iframe 而不是直接跳过去？**

- 门户目前**还没有 `/logout` 这个页面**（已登录状态访问返回 404）。直接跳过去用户会看到 404；
  放进隐藏 iframe 里就看不见了，用户最终落在门户登录页。
- 等门户补上 `/logout` 页面后，**这段代码不用改**：iframe 里那个页面会以同源身份调用
  `POST /api/auth/logout` 把门户会话清掉。

**为什么必须让"顶层窗口"跳转？**

门户把本应用注册成了 `open_mode=embedded`（iframe 内嵌）。如果只改 `window.location`，
门户的页面会被塞进那个小框里，看起来就是"点退出后门户界面还在、右边一块 404"——
这正是 2026-10-09 实际遇到的问题。

> ⚠️ 门户补上 `/logout` 之前，第 ② 步是空转（会静默 404），也就是**门户会话不会被清掉**：
> 退出后仍然可以直接点开其它接入应用而无需再输密码。补上页面即自动生效。

其余参数（询价数量、护栏、预期价格、名单）都可以在前端「参数设置 / 客户管理」里改。

### 状态监控页（`/monitor`）

仪表盘看"是什么状态"，`/monitor` 负责"怎么把它弄好"：

| 能力 | 说明 |
|---|---|
| 一键启动 | 依次 拉起浏览器（CDP 已通则跳过）→ 启动常驻监听 → 启动串行队列，幂等，可反复点 |
| 一键启动的浏览器步骤 | **先看 6901 被谁占着**：没占用直接起；占了但 CDP 不响应（僵死实例）先 kill 再起；本 profile 的残留 Chrome 一并清（否则新进程会接管旧实例、端口永远不开）；被**非 Chrome** 程序占用则拒绝并报出占用者；健康实例不打断 |
| 强制重启浏览器 | 不看是否健康，先把占用 6901 的进程与该 profile 的 Chrome 清掉，再起一个干净的（标签页会丢，登录态在 profile 里，不受影响） |
| 一键停止 | 先停常驻监听，再关浏览器；**有作业正在执行时拒绝关闭**（要强制得显式 `force`） |
| 四项检测 | 浏览器是否打开 / 1688 账号是否登录 / 登录态是否有效 / 页面是否打开 |
| 立即体检 | 额外读一次聊天页（只读）：核心文档在不在、会话列表能否读出、有没有登录框 |
| 打开聊天页 / 工作台 | 走串行队列新建标签页，不抢正在跑的任务 |
| Chrome 路径设置 | 填本机 `chrome.exe` 完整路径 / 一键恢复自动检测 / 重新检测候选；保存前会用与启动时**同一套判定**校验 |
| 1688 登录 | 一键：切「密码登录」页签 → 填账号密码（只填空着的）→ 点登录 → **自动拖动一次滑块** → 登录页切到前台；短信验证码人工完成 |

### 1688 掉线后的重新登录流程

1. 浏览器掉线时，状态监控页的「1688 账号登录 / 登录态有效性」会变红，仪表盘总开关也变红。
2. 点「一键登录」：脚本切到密码登录页签 → 只填**空着**的字段（Chrome 已记住的账号密码不动它）→ 点「登录」→
   把登录页切到前台 → 检测到滑块后**用模拟鼠标拖动一次**；若弹出「保持登录」会替你点「保持」（会话能撑更久）。
3. 如果滑块自动验证失败或出现短信验证码，再人工完成对应验证。
4. 登录态生效后本页会自动确认；也可以点「立即体检」：`登录态有效性` 变绿即可继续跑任务。

已实测的坑：点完登录后页面**看起来没变化**，其实是阿里风控把滑块放在同源 iframe
（`.../_____tmd_____/punish?x5secdata=...`）里；只看顶层文档会误判成"什么都没发生"。
现在的检测会递归扫同源 iframe，并读取手柄、轨道和 iframe 偏移；自动拖动失败时会明确报告
"卡在滑块验证"，不会把"看起来没变化"误当成已提交。

凭证可选：不填密码也能用（只要 Chrome 帮你记住了）；要填就存本机 `data/api.db` 的
`settings` 表，接口只回"有没有存"，绝不回显（`store.SECRET_SETTINGS` 过滤）。

两条运维注意事项：

1. **关浏览器只关调试实例**：优先用 CDP `Browser.close`；兜底才按进程关，
   且只认「占用 6901 端口的进程」或「命令行里带 `--user-data-dir=<CHROME_PROFILE_DIR>` 的 chrome.exe」。
   `CHROME_PROFILE_DIR` 默认 `%LOCALAPPDATA%\1688-cdp-profile`，必须与 `tools/qianniu/start-im.ps1` 保持一致。
2. **服务账号权限**：进程枚举走 `Get-CimInstance Win32_Process`。若运行账号读不到命令行
   （表现为页面提示"进程枚举不可用（WMI 权限受限）"），不影响体检与启停 ——
   端口占用进程是用 `netstat` 找的，只有"按 profile 关进程"这层兜底会失效（CDP 关闭仍然可用）。

### Chrome 路径的优先级

绿色版 / 装在非系统盘 / 多版本并存时，自动检测可能找不到 Chrome（默认只看
`Program Files`、`Program Files (x86)`、`%LOCALAPPDATA%` 三处的 Chrome 与 Chrome Beta）。
这时在「状态监控 → Chrome 路径设置」里填完整路径保存即可，优先级是：

1. **页面里保存的设置**（存在 `api.db` 的 `settings.chrome_exe`，改完立刻生效，不用重启）
2. 环境变量 / `.env` 里的 `CHROME_EXE`
3. 自动检测（前两处都空时）

> 保存时会用 PowerShell `Test-Path` 校验（和真正拉起浏览器时用的是同一个判断），
> 所以不会出现"保存时说能找到、点了启动又说找不到"。填错会直接拒绝并列出自动检测到的候选。

## 五、容器应用层 + Windows 宿主控制代理

```powershell
# 1. 在当前用户的桌面会话中启动宿主代理
.\deploy\start-host-agent.ps1

# 推荐：用户登录后自动启动，异常退出后每 5 分钟恢复
.\deploy\install-host-agent-autostart.ps1

# 2. 启动应用容器
docker compose --env-file .env -f deploy\docker-compose.yml up -d --build
```

### 职责边界

| 组件 | 运行位置 | 说明 |
|---|---|---|
| React + FastAPI + 队列 | Docker | 无 Windows 进程控制依赖 |
| Chrome / 1688 登录态 | Windows 宿主 | 保持桌面会话、人工验证码和持久化 profile |
| Node bridge / monitor | Windows 宿主 | 由宿主代理统一管理 |
| `im.db` | Windows 宿主 | 容器不直接挂载，代理生成 `VACUUM INTO` 快照 |
| 图片、短语、知识库 | Windows 宿主目录 | 只挂载这些静态业务文件，不挂载 SQLite WAL |

容器通过 `host.docker.internal:7400` 调用代理。代理使用 `HOST_AGENT_TOKEN`
认证；首次运行启动脚本会自动生成令牌并写入 `.env`。`7400` 只应对
Docker Desktop 或可信内网开放，不应直接暴露到公网。

### 关键行为

- `/api/browser/*` 的 Chrome 启停、进程检测仍执行原来的 Windows 脚本。
- `/api/flows/monitor/*` 仍启动/停止宿主 Node monitor。
- 所有 `bridge.call` 自动转发到宿主 Node bridge，容器内不再启动 Node bridge。
- SSO 一次性 `code` 的门户交换请求也由宿主代理发出；容器只接收交换后的 token，
  避免 Docker 到门户内网地址的路由差异造成登录循环。
- 容器每 2 秒拉取并校验一次 `im.db` 快照，原子替换本地副本，避免跨系统 WAL 锁。
- 容器停止或重启不会顺带关闭 Chrome、monitor 或宿主 bridge。
- 仍然只能运行一个 API 实例；进程内串行队列不能通过 Docker 副本扩容。

## 六、迁移到其他 Windows 虚拟机

1. 拷贝整个项目目录（含 `tools/qianniu` 与 `Automatic_Inquiry_System`）到目标机**相同盘符路径**下；
   换了路径的话，改 `.env` 里的 `PROJECT_ROOT` 即可，其余路径会自动推导。
2. 目标机装 Node >= 22、Python 3.12 与依赖。
3. 目标机 Chrome 用**独立 profile** 拉起并登录 1688：

```powershell
& "$env:ProgramFiles\Google\Chrome\Application\chrome.exe" --remote-debugging-port=6901 `
  --remote-allow-origins=* --user-data-dir="$env:LOCALAPPDATA\1688-cdp-profile" `
  --no-first-run --no-default-browser-check --new-window https://work.1688.com/
```

4. **在门户「应用管理」里把本应用的 URL 与回调地址改成新 IP**，并同步改 `.env` 里的 `SSO_CALLBACK_URL`。
5. 按第四节的步骤启动。

> 注意：同一账号不要在两台机器同时登录 1688，会被踢下线；
> 迁移时应先停掉旧机器的监听与系统。

## 七、排障手册

| 现象 | 原因 | 处理 |
|---|---|---|
| 仪表盘「Chrome 调试端口 6901」红 | Chrome 没起或没带调试端口 | 跑 `tools\qianniu\start-im.ps1`，确认 6901 可访问 |
| 「常驻消息监听」红、客户数与消息数不增长 | 监听进程没起 | `tools\qianniu\start-im.ps1 -Interval 15000 -RefreshMin 0` |
| 「Node 桥接进程」红 | 桥接崩了或 Node 版本太低 | 看「参数设置 → 运行环境 → 桥接脚本」路径是否存在；`node -v` 需 >= 22；重启服务 |
| 登录后立刻跳回登录页 | `JWT_SECRET` 两边不一致 | 与门户 `.env` 对齐后重启本服务 |
| 点「企业门户登录」回来是 403 | 门户里没注册本应用，或角色不匹配 | 在门户「应用管理」注册与回调**同源**的地址；按需绑定角色 |
| 接口一直 401 | cookie 没带上 | 确认浏览器访问的是 `http://IP:6900` 而不是别的端口；跨域部署时需用 `CORS_ORIGINS` |
| 点「启动任务」报「浏览器正被另一个流程占用」 | 有别的 Node 进程也在动浏览器 | 停掉多余的进程；本系统内所有浏览器动作都是串行的 |
| 队列一直显示「执行中」不动 | 某个浏览器动作卡住（页面异常/未登录） | 前端点「刷新聊天页」，或在任务列表点「收敛标签页」；仍不行则重启监听与桥接 |
| `database is locked` | 容器 bind mount 下的 SQLite 锁问题 | 改回原生运行（推荐）；或降低并发查询频率 |
| 图片缩略图裂图 | 图片路径不在图片库目录内 | 把图片放进 `tools/qianniu/image/`，在「图片库」点「同步文件夹」 |
| 消息重复统计 / 客户错位 | 会话没切换成功就被读了 | 系统已内置校验（比对 `activeConvId`）；若仍出现，降低参数里的「同时处理会话数」，减少单个队列轮转步的工作量 |
| 点「一键启动」后 Chrome 没起来：状态监控报「调试端口 6901 不通，也没找到该 profile 的 Chrome 进程」 | **跑 API 的那个进程没有桌面权限**（从受限会话 / 计划任务 / 服务方式启动的），`Start-Process chrome.exe` 会静默失败 | 在**你自己的 PowerShell 窗口**里重启 API：`pwsh -File deploy\start-native.ps1`。页面上的步骤详情会直接给出这个病因（2026-10-15 加） |
| 「停止监听」提示成功，但监听进程还在跑 | 旧版用 `powershell.exe`（5.1）执行冻结的 `start-im.ps1`，它含中文且无 BOM，5.1 按 GBK 读会整脚本**解析失败**，而代码又不看退出码 | 已修（2026-10-15）：停止/状态改用纯 ASCII 的 `deploy/monitor-control.ps1`，启动由 Python 直接拉起 node；接口失败会真的报错 |
| 点「启动监听」接口超时，但监听其实起来了 | 旧实现里 `Start-Process` 起的 node 继承了 PowerShell 的 stdout 管道，Python 侧等不到 EOF | 同上，已改为 Python 直接拉起（句柄继承可控） |
| 用 `powershell.exe` 跑 `deploy\start-native.ps1` 报一堆 `Unexpected token` | 5.1 按系统 ANSI 代码页读无 BOM 的含中文 .ps1 | `start-native.ps1` 已加 UTF-8 BOM（5.1/7 都能跑）；`tools\qianniu\start-im.ps1` 是冻结源码不能动，请用 `pwsh`（PowerShell 7）跑 |

| 1688 常驻监听 | `tools\qianniu\logs\monitor.out.log`、`monitor.err.log` |
| 事件流水（JSONL） | `tools\qianniu\logs\im-events.jsonl` |
